EFS throughput vs storage class — separate knobs - throughput mode: Bursting (credits, spiky) · Elastic (auto) · Provisioned (fixed, pay more) - performance mode: General Purpose (low latency, default) · Max I/O (high parallel, higher latency) - storage class: Standard · IA · Archive → cost of storage only, no throughput effect - "spiky bursts, low average, no manual provisioning" → Bursting + General Purpose + Standard

New in Test 5 (not in bank / T1–T4)

Kinesis producer errors - ProvisionedThroughputExceededException from sending records one at a time at high rate → fix is PutRecords batching, not adding shards - only reshard if batching alone still exceeds per-shard limits (1,000 records/sec or 1 MB/sec write)

EBS encryption scope - encrypts: data at rest, all snapshots, and data in transit between the volume and the instance - HIPAA/compliance questions naming "volume to instance" traffic → still covered, no extra step needed

File exchange modernization (SFTP) - Linux-only shared file system → EFS, not FSx for Lustre (Lustre = HPC scratch, not general shared storage) - AWS Transfer Family SFTP → run inside a VPC with EIPs, not "public endpoint" - user-level file permissions → POSIX identity mapping (EFS) + IAM policy, not plain SG-only

EC2 Instance Connect mechanics - pushes a temporary public SSH key to the instance (60-second validity) via API, then you connect over the instance's public IP (or via Instance Connect Endpoint for private IP without one) - doesn't require SSM Agent, doesn't need "disabling" anything — it's a separate, simpler mechanism than Session Manager

Built-in EC2 recovery actions on CloudWatch alarms - CloudWatch alarm actions on an EC2 instance can directly: Reboot, Stop, Terminate, Recover — no Lambda/EventBridge needed - "auto-restart on failure, simplest" → CloudWatch alarm + native alarm action, not a custom Lambda poller

RDS DR — Region scope - Multi-AZ = same-Region HA, not DR - automated backups can be configured to copy cross-Region — that's what makes it disaster recovery capable - "resilient from a DR perspective" → must include cross-Region, not just Multi-AZ

KMS request-cost optimization - S3 Bucket Keys — one KMS-generated key reused per bucket for many objects, cuts KMS API call volume/cost while staying on SSE-KMS - switching to SSE-S3 loses KMS features (audit trail, key rotation control, cross-account key policies) — not the fix if KMS control must stay

Aurora HA terminology - Aurora has no "Multi-AZ standby" concept like standard RDS - HA = Aurora Replica (up to 15, can be manually or auto promoted to writer on failover) - if a question says "standby" for Aurora specifically, it's the wrong term/wrong option

Session Notes — Q&A during Test 5

IAM identity services — quick differentiation - IAM Identity Center — your employees logging into AWS accounts/console (Org-wide SSO) - AD Connector — on-prem AD exists, people log into AWS apps with existing creds (proxy only, no AWS-side directory) - Managed Microsoft AD — actual AD running in AWS for workloads (domain join, SQL Server) and/or trust relationship - test: "log into AWS console/apps" → Identity Center/AD Connector. "Workload needs AD/domain join/trust" → Managed Microsoft AD

ASG unhealthy-not-replaced — real vs fake causes - real: Impaired (waits to self-recover) · health check type=EC2 default (ignores ELB failures) · grace period after launch - fake/distractor: needing custom health checks, being Spot, raised minimum capacity

RAM shared subnet — when it's "cheapest" - multiple accounts (same Org) need EC2 in the same subnet/network, privately, cheapest → RAM shared subnet (no hourly charge, just IAM-level sharing) - vs 2 VPCs need connectivity cheapest → Peering; many VPCs/transitive → Transit Gateway

CloudFront on an API (EC2/ALB origin) - yes — helps even for APIs: edge TLS termination, keep-alive to origin, caching for cacheable GETs, WAF/DDoS at edge - for a single-Region API, Global Accelerator also helps (routes onto AWS backbone) — the "GA is TCP/UDP only, doesn't help HTTPS" idea is a misconception; HTTPS runs over TCP, GA works fine - Route 53 has no role improving performance for a single-Region deployment (nothing to choose between)

Subnet/route table basics - route tables associate at the subnet level, not per instance - public subnet = route table has 0.0.0.0/0 → IGW + instance has public/EIP - private subnet = route table has 0.0.0.0/0 → NAT GW (or no route) - IGW attaches at VPC level but only enables internet for subnets whose route table points to it - NACL is stateless — must explicitly allow both directions on custom NACLs (default NACL allows all)

Sentiment analysis / audio-to-SQL - automated sentiment scoring, managed, no ML expertise → Comprehend - "convert audio to text then ad-hoc/exploratory SQL analysis" (not sentiment scoring) → Transcribe + Athena - QuickSight = BI/dashboards only, not a SQL query engine or sentiment tool

Caching geospatial data - ElastiCache for Redis — native GEOADD/GEORADIUS/GEODIST commands - Memcached does not support geospatial

RDS Multi-AZ failover - DB endpoint/URL never changes — only what the CNAME resolves to (standby's IP) changes internally - watch wording: "URL will change" (false) vs "CNAME target updated, URL unchanged" (true)

Storage for 3 different needs in 1 scenario - max I/O performance (scratch/processing) → Instance Store - durable storage → S3 - archive → Glacier - don't try to solve all three needs with different S3 storage classes alone — S3 itself isn't a performance tier

POSIX - Linux/Unix-style permissions (owner/group/other, rwx) — not Windows - this is why EFS is POSIX/Linux-only; FSx for Windows exists separately for NTFS ACLs

Error-page routing (R53) - active-passive (failover routing policy + health check) — not active-active/weighted

Reporters upload/download 500MB videos, remote offices - correct (2 valid): CloudFront (supports PUT/POST too, not download-only) AND S3 Transfer Acceleration - wrong: per-Region separate buckets, EC2+EBS relay jobs - S3TA = S3-specific, no caching, simplest. CloudFront = general edge network, adds caching — both valid for many up+down questions, check for multi-select before eliminating one

WAF attachment points - CloudFront, ALB, API Gateway (REST only, not HTTP API), AppSync, Cognito User Pool, Verified Access - not directly on EC2 or NLB - if no CloudFront in stem → WAF on ALB/API Gateway; if CloudFront exists → WAF on CloudFront is usually the "earlier/more complete" answer - watch for absolute words in options ("only," "cannot," "always") — often the actual trap, not the architecture choice

IAM Access Advisor vs Access Analyzer - Access Advisor — what a specific user/role has actually used recently (rightsizing, removing unused perms) - Access Analyzer — scans policies to find resources shared externally (cross-account/cross-org exposure) - "unused permissions" → Advisor. "unintended external sharing" → Analyzer

Kinesis Enhanced Fan-Out - multiple consumer apps on the same stream sharing the 2 MB/s per-shard pipe → contention/lag → Enhanced Fan-Out gives each consumer its own dedicated 2 MB/s - different from producer-outpacing-consumer (fix = more shards + more consumer parallelism), read which noun ("consumers," plural) the lag is about

S3 lifecycle "immediate access" trap - "rarely accessed" alone doesn't mean Glacier — check if immediate/instant access is also required - rarely accessed + instant access → Standard-IA (ms retrieval, just costs more per-GB retrieval) - rarely accessed + retrieval delay OK → Glacier tiers

ALB vs ASG health checks — the anomaly pattern - ALB target group health check and ASG health check are two independent systems - ALB always uses its own target-group health check (HTTP ping) — that's normal, not a bug - ASG defaults to EC2 health check type, ignoring ALB's verdict entirely, unless explicitly set to ELB type - "ALB removes instance from pool but ASG doesn't replace it" → ASG health check type is still EC2 (default)

Spot + SQS "no downtime" — how that's true - "no downtime" refers to the system, not any single instance - SQS visibility timeout means an interrupted Spot instance's in-flight message just becomes visible again and gets reprocessed — no data loss, brief delay only - "withstand interruptions, queue-based/decoupled/batch" → Spot is safe; synchronous user-facing (no queue buffer) → Spot is wrong

New in Test 6 (not in bank / T1–T5)

GuardDuty vs WAF - GuardDuty = threat detection (analyzes VPC Flow Logs, DNS logs, CloudTrail for malicious activity like crypto-mining IP calls, compromised credentials, port scanning) - WAF = blocks/filters web requests by rule (rate, IP, geo, SQLi/XSS) — doesn't "detect" background malicious behavior like DNS queries to known bad IPs - "EC2 instance querying/calling known malicious IPs" → GuardDuty, not WAF

EBS Multi-Attach - lets multiple EC2 instances (same AZ) attach the same EBS volume simultaneously - only supported on io1/io2 (Provisioned IOPS) — never gp2/gp3/st1/sc1 - app must handle concurrent write coordination itself (needs cluster-aware filesystem)

AWS Alternate Contacts - per-account contacts for Billing / Operations / Security, separate from root email - built specifically to fix "critical alert went to root email nobody watches" - pair with a root-email alias forwarding to a monitored mailbox for defense in depth

User data run-once behavior - user data scripts run once, at first boot, by default — no extra config needed - re-running on every boot requires special opt-in (cloud-init directives), not default - "run custom script only once at launch" → plain user data already satisfies this

SQS priority pattern - SQS itself has no native priority — build it with two separate queues (Standard, not FIFO — ordering ≠ priority) and have consumers poll the high-priority queue first, falling back to the low-priority one - FIFO would only matter if strict ordering within a class were required, which this scenario doesn't ask for

RDS Multi-AZ OS patching sequence - AWS patches the standby first → promotes standby to primary (brief failover) → patches the old primary (which is now the new standby) - this is how zero/minimal-downtime patching works — not simply "replication keeps them in sync"

Single-instance monolith HA pattern - app can't run on >1 instance at once → ASG min=1/max=1/desired=1 (self-healing single instance, not scaled) - attach a fixed Elastic IP via EC2 user-data script on boot so the IP follows to whichever instance ASG launches - no ALB — ALB implies routing across multiple targets, which breaks a non-distributed app

ElastiCache engine choice — threading - Redis = single-threaded (per node), rich data structures (sorted sets, geospatial, pub/sub), persistence, replication - Memcached = multi-threaded, simple key-value only, no persistence, no replication — but scales better across CPU cores for pure caching - "multi-threading" explicitly required → Memcached, even though Redis is the "richer" default answer everywhere else

Bastion host load balancer type - bastion = SSH (22) / RDP (3389), pure TCP, not HTTP - ALB is L7 (HTTP/HTTPS) — wrong fit - HA bastion → NLB (L4) + ASG

Direct Connect VIF for S3 access - Public VIF — reach AWS public service endpoints (S3, DynamoDB) over DX, still private/dedicated path, no public internet - Private VIF — reach resources inside a VPC (via VGW) - "access S3 directly over DX, no internet" → Public VIF, not Private VIF + VPC endpoint (VPC endpoints are irrelevant to on-prem-via-DX)

Dedicated Instances vs Dedicated Hosts - Dedicated Instances — physical isolation, but you don't control/see the underlying host ID, so can't track socket/core/host affinity for licensing - Dedicated Hosts — full visibility and control of the physical host (ID, sockets, cores) — required for BYOL / per-socket/per-core licensing - "bring existing server-bound licenses" → always Dedicated Hosts, not Dedicated Instances

VPC DNS attributes - enableDnsSupport — enables Route 53 resolution within the VPC (required for private hosted zones to work) - enableDnsHostnames — assigns DNS hostnames to instances - there is no enableDnsDomain attribute — distractor/fake name

Spot Fleet composition - Spot Fleet can request Spot Instances only, or a mix of Spot + On-Demand, across multiple instance types/pools - "Spot Fleet = Spot only" is a false absolute — watch for this pattern generally (see Blind Spot 17)

Session Notes — Q&A during Test 6

Multi-site AWS connectivity (DX + 2× VPN) - central hub → Transit Gateway (attach DX via Transit VIF + both VPN connections) - if TGW not offered as an option and multiple Site-to-Site VPNs terminate on one VGW needing to reach each other → legacy AWS VPN CloudHub

SQS queue types — the only two real types - Standard (nearly unlimited throughput, at-least-once, best-effort order) and FIFO (strict order + exactly-once, 300/3,000 batched, up to ~70k/s with high-throughput mode) - DLQ, delay queues, temporary queues = features/add-ons, not alternative "types" — don't let an option imply otherwise - Temporary Queue Client — auto-deleting, lightweight queues for high-throughput request-response patterns (real, not a distractor — correct answer in both T6 Q9 and earlier T6 dupe)

Athena + storage classes - queries S3 Standard, Standard-IA, One Zone-IA, Intelligent-Tiering directly - cannot query Glacier tiers without restoring first

Concept Notes

Savings Plans vs RI

  • database → RI only (no SP for RDS/Redshift/ElastiCache/OpenSearch)
  • flexible / Lambda / Fargate → Compute SP (66%)
  • locked family+Region, bigger discount → EC2 Instance SP (72%)
  • capacity guarantee in one AZ → RI
  • interruptible → Spot
  • ~2.5% of questions. Don't over-invest.

SNS · SQS · EventBridge · Step Functions

  • SQS — 1 message → 1 consumer. Many pollers = share work, not broadcast
  • SNS — copy to every subscriber. Fan-out combo: SNS → many SQS
  • EventBridge — AWS events, schedules, content-based routing
  • Step Functions — multi-step, retries, waits. Chaining Lambdas = wrong answer
  • EventBridge starts things · Step Functions orders things

Kinesis

  • Firehose → S3, Redshift, OpenSearch, Splunk, HTTP. Never DynamoDB
  • Data Streams → replay, multiple consumers, custom processing
  • Firehose doesn't need Data Streams in front
  • shard = one lane · partition key picks the lane · order within shard only · bad key = hot shard

Databases

  • Aurora = RDS family · RDS Proxy supports it
  • Aurora = MySQL/PostgreSQL only, never SQL Server
  • Aurora Global = 1 writer · DynamoDB Global Tables = write anywhere
  • too many connections (esp. Lambda) → RDS Proxy
  • Multi-AZ = availability · read replica = performance
  • Multi-AZ engine upgrade = both at once, downtime. Not rolling
  • Redshift speaks SQL too — SQL alone identifies nothing
  • OLTP → RDS/Aurora · warehouse/MPP → Redshift · files in S3 → Athena
  • RDS storage autoscaling = opt-in feature · Aurora storage = automatic to 128 TiB
  • unpredictable compute → Aurora Serverless v2

Read replica vs cache

  • same data repeatedly → ElastiCache (DynamoDB → DAX)
  • many different reads / reporting → read replica
  • "no app changes" → read replica (cache needs cache-aside code)
  • microseconds → cache · milliseconds fine → replica

Storage

  • SMB = Windows · NFS = Linux
  • SMB/AD/DFS/NTFS → FSx Windows
  • NFS simple → EFS
  • HPC/EDA/chip design/genomics → FSx Lustre (+S3 link for cold)
  • both SMB+NFS → FSx NetApp ONTAP
  • EFS = regional · cross-Region DR → EFS Replication
  • EFS access = SG (port 2049) + IAM policy · access points = POSIX user/dir
  • highest random I/O + replicated/re-creatable → Instance Store

S3 lifecycle

S3 Standard ┌──────────────┴──────────────┐ ▼ ▼ Standard-IA ──────────────▶ Intelligent-Tiering └──────────────┬──────────────┘ ▼ One Zone-IA ▼ Glacier Instant Retrieval ▼ Glacier Flexible ▼ Deep Archive

  • nothing returns to Standard
  • Standard-IA → Intelligent-Tiering = only sideways move (not reverse)
  • One Zone-IA = dead end, Glacier only
  • 30 days in Standard before IA · <128 KB not transitioned
  • min charge: Standard none · IA/One Zone 30d · Glacier IR 90d · Flexible 90d · Deep Archive 180d
  • no wait required before moving to Deep Archive — 180d is a billing minimum

S3 Object Lock

  • retention on the object version, never "the object"
  • bucket default = duration · version = Retain Until Date
  • explicit beats bucket default
  • needs versioning
  • Governance = overridable with permission · Compliance = nobody, not even root
  • Legal hold = no date, on/off
  • was correct 9/9 in the bank

S3 misc

  • uploads free · only egress costs
  • S3TA bills only if it actually accelerated
  • cache S3 → CloudFront (no DAX equivalent)
  • One Zone-IA wrong 19/19 in the bank — trap
  • encryption: SSE-S3 (free, no audit) · SSE-KMS AWS key · SSE-KMS customer managed key = audit + rotation + revoke · SSE-C (you send key, AWS stores nothing, no rotation) · CSE
  • customer managed key (in KMS) ≠ customer provided key (SSE-C)

Networking

  • content-based routing → ALB only (path, host, header, query, method, source IP — not body)
  • UDP → NLB or Global Accelerator only
  • GA = static IP, IP allowlist, instant failover, TCP/UDP, keeps own DNS
  • R53 = DNS routing policies, slow failover (TTL)
  • Direct Connect not encrypted → "dedicated + encrypted" = DX + VPN
  • same-AZ private IP free · cross-AZ $0.01/GB each way · public IP charged even same-AZ
  • CloudFront custom origin can be on-prem (must be publicly reachable)
  • SG (instance, allow only) → NACL (subnet, only thing that denies an IP) → Network Firewall (VPC, IDS/IPS)
  • geo: R53 routes · CloudFront geo restriction blocks · WAF blocks — pick by what's in the architecture
  • R53 Resolver: VPC→on-prem names = outbound · on-prem→AWS names = inbound

  1. pipe — Direct Connect (dedicated, weeks) · S2S VPN (encrypted, quick) · Client VPN (laptops)
  2. data — Storage Gateway (use cloud storage locally) · DataSync (scheduled copy) · Snowball (offline bulk) · DMS (database)

Recurring Blind Spots
  1. Not checking S3 minimum durations — cost questions turn on 30/90/180, not per-GB price
  2. Assuming an integration exists — Firehose→DynamoDB, "Athena ML". Check the pairing is real
  3. Skimming the architecture in the stem — WAF vs CloudFront was decided by what's already deployed
  4. Treating serverless as infinite — Lambda 1,000 concurrency, FIFO 300/s. Numbers in the stem = recall a limit
  5. Reaching for the bigger service — SageMaker over Comprehend, DynamoDB over Aurora. "Minimal change" → simpler wins
  6. Over-restricting on security — "remove access for everyone" is almost always wrong; want boundaries/SCPs/scoped policies
  7. Repeat misses (T1→T2) — RAM, AZ math, Shared Services VPC, Multi-AZ upgrade, Hibernate, launch config. Re-read these before Test 3
  8. Legacy-name traps — Transit VPC vs Transit Gateway, launch configuration vs launch template, customer managed vs customer provided key
  9. Metric source precision (new T3) — which entity emits the metric (ECS Service, not ALB/alarm; System check, not instance check)
  10. Direction confusion (new T3) — R53 inbound vs outbound. Note: CloudFront also supports PUT/POST, so it CAN accelerate uploads too — S3TA vs CloudFront isn't upload-vs-download, it's "S3-only, no cache, simplest" (S3TA) vs "general edge network, adds caching" (CloudFront). Both valid for many up+download questions — check for multi-select before eliminating one

  11. Over-engineering encryption (new T3) — SSE-S3 already gives per-object keys; don't reach for KMS context
